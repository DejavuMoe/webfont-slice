# 分包算法

CJK 字体的难点不在"切"，而在"切在哪里"。一款中文字体有几千到三万个字形；一个页面通常只用到其中几百个，但哪几百个无法预先知道。`unicode-range` 让浏览器只下载命中的分片，于是问题变成：**怎样划分字符，使典型页面下载的字节和请求都尽量少。**

片数太少，每片都会被命中，等于下载整款字体；片数太多，每片的固定开销、请求成本和丢失的压缩上下文累积起来。WebFont Slice 把这个权衡写成一个可计算的目标函数，并用这款字体实测校准的体积模型求解。实现位于 `src/core/shard-planner.ts`。

## 页面模型

把一页正文看作从字符使用分布 `p` 中独立抽取 `L` 个字符。某个分片包含的字符概率之和（质量）为 `m` 时，它在这一页被下载的概率为

```text
P_L(m) = 1 − e^(−L·m)        （泊松近似）
```

`p` 来自字频数据（简体 SUBTLEX-CH，繁体为其 OpenCC 派生档案，见 [`DATA.md`](./DATA.md)）；用户粘贴的站点文本达到 200 字后按长度混入，最多占 40%。计划面板的"每页预计下载"就是 `Σ P_L(m_i) · bytes_i`，页面长度可选 300 / 1500 / 6000 字。

## 切分

字符分为三类：

1. **基础字符**：ASCII 与常用中西文标点。几乎每页都会出现，单独成片并建议预加载。
2. **有字频依据的字符**：按使用概率降序排成序列，在序列上求最优的连续切分。
3. **长尾**：语料中没有出现的字符。按码点顺序装箱到粒度对应的大小。码点相邻的汉字按部首排列、共享部件，这样装箱既让 `unicode-range` 压缩成少量连续区间，也让 WOFF2 压缩得更好（实测约省 5–10%）。装箱跨入另一个文字分组（`scriptFamily`：拉丁、希腊、西里尔、其他字母文字、标点符号与制表符、CJK、谚文、私用区图标、表现形式、表情）时，只要当前片不小于 `max(2 × overhead, minBytes / 4)`（默认档约 6 KB）就切开：一个页面很少同时用到两种非拉丁文字，俄文页面不必顺带下载半片希腊文，终端界面不必顺带下载图标。

西文字体（拉丁正文字体、代码等宽字体、图标字体）几乎没有字频依据：ASCII 与常用标点进基础片，其余全部是长尾，因此实际效果就是按文字分片，与主流网页字体服务的 latin / latin-ext / greek / cyrillic 子集划分接近。

对第 2 类，动态规划在所有连续切分中最小化

```text
Σ  P_L(m)  · (overhead + bytes + requestCost)      首访这一页的期望代价
 + 0.3 · P_8L(m) · (overhead + bytes)              同一访客随后浏览若干页的累计下载
 + 96                                               每条 @font-face 在 CSS 中的常驻成本
```

并约束单片大小在粒度档位的 `[minBytes, maxBytes]` 内。

- 只看首访会把中频过渡区切成大量几个字一片的碎片（独立抽样假设低估了字符共现）；会话项让这些区域合并成合理的大小。
- `maxBytes` 让高频区即使总会加载，也拆成几个文件，保证渐进渲染。
- 为了把 DP 控制在毫秒级，相邻字符先聚成 0.5–4 KB 的原子（约 2400 个以内）；规划 3 万字的字体约 10–40 ms。

结果的形状是：高频区合并为少数几个大片（几乎每页都会加载，少发请求），中频区切细（按需加载，少浪费），长尾装箱成较大的片（很少被加载）。

`requestCost` 是把一次请求折算成的字节数。HTTP/2、HTTP/3 下请求很便宜，默认档位偏向省流量；仍在使用 HTTP/1.1 的站点应调向"最少文件"。

### 单文件

把全部字符打成一个文件，适合只有少量文字的标题与 Logo。界面在"分包方式"里提供；字符集很小、文章页仍会加载大部分分片时，计划面板会主动建议。

### 预加载与多款式

- 基础片与加载概率 ≥ 90% 的分片建议预加载，最多 3 个文件。
- 可用字符集合相同的款式（例如同一家族的多个字重）共享一套切分，`unicode-range` 一致，各自估算体积。

## 体积模型

规划需要在子集化之前知道"任意一组字符打包后有多大"。模型为

```text
bytes(shard) ≈ overhead + ratio · Σ raw(c) · scale(c)
```

- `raw(c)`：直接读取字体表得到的字形原始字节：glyf/loca 的轮廓，CFF/CFF2 的 CharString，可变 TrueType 再加上 `gvar` 中的变体数据（保留可变轴时计入）。
- `overhead`、`ratio`：体检时对这款字体实测子集化两次（单字、均匀抽样 240 字）求出。
- `scale(c)`：两个同样实测得到的修正。
  - **连续码点**：连续 240 个码点打包，相邻字形共享部件，压缩更好；实测系数 0.90–0.95，作用于长尾片与单文件。西文字体的长尾横跨多种文字，压缩率差别很大（重音字母多为组合字形，制表符、盲文高度相似），因此再按文字分组各测一次（`familyRunScales`，代码字体实测 0.3–0.9），未测到的分组用整体系数。
  - **基础字符**：拉丁字母与标点带有字距等布局数据，按字形字节估算会偏差；实测系数 0.83–1.43，作用于基础片。
- 整款字符放进一个文件时，Brotli 可以跨越全部字形寻找重复。超过 1 MiB 的单文件按 `(bytes / 1 MiB)^−0.1` 折减。这是在 3 款字体、17 个单文件上拟合的经验式。

"相比单文件"使用这个单文件估算作为基准，而不是分片体积之和：分片之和比真实单文件大 10–35%，拿它比较会高估分包的收益。

字频模型来自中文语料，对西文字体只能区分"基础字符"与"其余"；页面若只有 ASCII 与常用标点，只下载基础片（相比单文件 −65%），用到重音字母、希腊或西里尔文、制表符时再各加一片。等宽字体的连字（`calt`/`liga`）只在同一片内生效，而 ASCII 全在基础片，`=>`、`!=`、`<=` 这类代码连字不受分片影响。

切分方式变化对 CJK 字体的影响（Noto Sans SC Variable，实测）：按字表取字的场景（规范一级、全表、GB 18030、繁体台湾）切分与体积完全不变；"字体全部字符"的长尾在拉丁、希腊、西里尔、符号、谚文与私用区边界多切出 4 片（178 → 182），总量 +0.1%，文章页 891.0 → 890.8 KB；Noto Serif SC Variable 的"字体全部字符"为 245 → 248 片。

- 按码点顺序切分时，常用字散落在几乎每一片里，文章页要下载约 90% 以上的分片。

- 按字频等大在 300 字的短页上字节略少（例如 666 KB 对 698 KB），代价是请求数翻倍。

## 复现

```bash
pnpm benchmark:planner path/to/font.ttf                         # 只做规划，几秒
pnpm benchmark:planner path/to/font.ttf --measure               # 逐片实测，大字体需要几十秒
pnpm benchmark:planner path/to/font.ttf --scenario sc-full,tc-tw-common,sc-gbk --json
```

场景写法：`<语言>-<档位>`（`sc` / `tc-tw` / `tc-hk` × `common` / `full`）、`font-all`、`western-common` / `western-full`（西文字体的西欧与多语言档），或任意字表 ID（如 `sc-gbk`，自动附带拉丁与标点基础字表）。不指定场景时，西文字体默认跑 `western-common,western-full,font-all`。脚本通过 Vite SSR 直接加载 `src/core` 与 `src/engine`，与界面使用完全相同的规划器和体积模型。基准字体不提交仓库：Noto Sans SC / Noto Serif SC Variable 来自 Google Fonts（OFL），等线来自 Windows 系统字体，JetBrains Mono 2.304 与 Fira Code 6.2 来自各自的 GitHub Releases（OFL）。

## 性能

> 测于 2026-09-26：Windows 11 + WSL2（Debian）、Node.js 24、Chromium（Playwright）。结果受 CPU、内存与字体表复杂度影响，只用于判断量级与回归。

线程池按 `core/threads.ts` 选择线程数：最多 6 个且不超过核心数 − 1；每线程预算 `24 MB + 3.2 × 字体体积`（HarfBuzz 每次调用把字体复制进只增不减的 WASM 堆），总预算按 `navigator.deviceMemory` 取 1400 / 720 / 320 MB。

浏览器内实测（Noto Sans SC Variable，17 MB；8 核、8 GB，线程池选择 6 线程；含 FontFace 验证与哈希）：

| 任务                               |  耗时 |
| ---------------------------------- | ----: |
| 体检 + 体积校准（含首次加载 WASM） | 1.5 s |
| 常用 · 3,701 字 · 26 片            | 1.0 s |
| 完整 · 8,306 字 · 65 片            | 3.1 s |
| GB 18030 · 27,759 字 · 171 片      | 8.4 s |

每片耗时主要由"把整款字体复制进 WASM 堆并建立子集化计划"决定，与分片大小关系不大；片数越多总耗时越长，多线程接近线性加速（171 片单线程 34.8 s，6 线程 8.4 s）。规划本身在主线程同步运行：相邻字符先聚成 0.5–4 KB 的原子（不超过约 2400 个），3 万字的字体也只需 10–40 ms，因此四档对比与粒度滑杆都能实时更新。

内存：输入上限 100 MB；归一化结果超过 64 MB 时提示移动设备风险；每个线程保留一份字体，HarfBuzz 堆峰值约为字体体积的 2–3 倍，空闲 8 秒后回收线程。

前端体积（`pnpm build`，2026-09-27）：首屏应用 JS 120 KiB gzip（预算 ≤ 300 KiB），CSS 8.6 KiB gzip；Engine Worker 308 KiB、HarfBuzz WASM 220 KiB gzip 在加入第一个字体时加载，WOFF2 编码 WASM 300 KiB gzip 在校准或生成时加载；PWA precache 53 项 / 2.9 MiB。WASM 保持独立静态资产，不内联进 JS。

## 局限

- 独立抽样忽略了字符共现：同一篇文章的用字比随机抽样更集中，实际下载通常低于期望值。
- SUBTLEX-CH 是影视字幕语料，偏口语；专业领域站点建议粘贴自己的文本参与字频。
- 繁体字频由简体语料映射而来，不是独立的繁体语料。
- 没有西文字频：西文字体的每页数字只反映基础片，重音字母、希腊与西里尔文按"很少用到"处理。面向法语、德语、越南语等站点时，把站点文本粘贴进"你的文本"可以让这些字母进入有字频依据的分片。
- 体积模型的经验参数（会话权重、单文件折减）在 3 款字体上拟合，其他字体可能有几个百分点的偏差；生成后界面与报告显示的都是实测体积。
